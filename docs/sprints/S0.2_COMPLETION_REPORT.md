## 1. Executive Summary

Sprint 0.2 has been completed in full. The objective was to construct a clean, generic, reproducible conventional RAG pipeline that will serve as the **experimental control** for all future Aryntra Synapse research sprints.

The system is functional, tested, committed, tagged, and pushed to GitHub. No experimental features were introduced. The implementation is intentionally minimal. Every architectural decision was made to preserve research integrity, not to maximise capability.

The baseline is frozen at `v0.2.0`.

---

## 2. Objective

The sprint was not building Synapse itself.

It was building the system against which Synapse will be measured.

The requirement was a conventional RAG pipeline implementing exactly this flow and nothing more:

```text
User Query
    ↓
Embedding
    ↓
FAISS Similarity Search
    ↓
Top-K Chunks
    ↓
Context Assembly
    ↓
Local LLM
    ↓
Answer
```

No graph. No compression. No reranking. No adaptive logic. No agent loop.

## 5. Architecture Decisions

### 5.1 Component isolation

Each layer was built to be independently testable and independently replaceable.

```text
chunking.py      knows about: text, config
embeddings.py    knows about: text, numpy
retriever.py     knows about: embeddings, faiss, chunks
ollama_provider  knows about: question, context string, ollama
routes.py        knows about: all of the above — wires them together
```

No circular dependencies. No layer reaching across its boundary.

This was a deliberate research decision. When S1 introduces a new context representation layer, it slots in between `retriever.py` and `ollama_provider.py` without touching anything else.

### 5.2 Structured retrieval results

Retrieval results are not immediately collapsed into a string.

Each result preserves:

```python
{
    "chunk_id": "doc1_chunk_003",
    "text":     "...",
    "score":    0.87
}
```

This is critical for future sprints. Relationship layers, compression layers, and provenance tracking all require access to individual chunk identity and similarity scores. Destroying that information at the retrieval stage would require architectural reconstruction later.

### 5.3 Context assembly is intentionally dumb

The baseline assembles context as:

```text
[Chunk 1]
...

[Chunk 2]
...

[Chunk 3]
...
```

No summarisation. No compression. No reranking. No relationship annotation.

This is the control condition. The experimental value of S1 onwards depends entirely on this baseline being as simple as possible.

### 5.4 Generic prompt

The LLM prompt was deliberately generalised:

```text
You are a helpful assistant. Answer the question using only
the context provided below. If the context does not contain
enough information to answer the question, say so clearly.
Do not invent facts that are not supported by the context.
```

The previous prototype contained a medical-specific system prompt. That was removed. Synapse is a generic research framework.

### 5.5 Measurement built in from day one

Every API response returns:

```json
{
  "retrieval_latency": 0.0179,
  "generation_latency": 57.4471,
  "total_latency": 57.4652,
  "context_length": 1570,
  "num_chunks_retrieved": 3
}
```

These measurements exist now because we will need them the moment compression experiments begin. Retrofitting measurement into a running system is expensive and error-prone. It was cheaper to build it into the baseline.

## 6. Known Characteristics of the Baseline

The following observations were made during manual end-to-end testing. They are documented here as baseline characteristics, not defects.

### 6.1 Mid-sentence chunk boundaries

Character-based chunking cuts across word and sentence boundaries. Retrieved chunk text may begin or end mid-sentence.

```text
"ctual accuracy.\n\nFAISS\n------\nFAISS, which stands for..."
"ameters, RAG systems first retrieve relevant documents..."
```

This is expected behaviour. The retrieval still returns semantically relevant content. This characteristic is documented as a known limitation of flat character chunking and is a candidate for investigation in future sprints.

### 6.2 Generation latency

```text
generation_latency: 57.4471s
```

Mistral running locally on CPU produces generation latency in the range of 50—60 seconds per query. This is an infrastructure characteristic of the development environment, not a system defect. It is recorded here as the baseline measurement against which future optimisations can be compared.

### 6.3 Retrieval latency

```text
retrieval_latency: 0.0179s
```

FAISS retrieval over 10 chunks is effectively instantaneous. This number will become more meaningful at scale.

## 11. Reproduction Instructions

Any developer can reproduce the baseline from scratch:

```powershell
git clone https://github.com/raghavendrashivam474/aryntra-synapse.git
cd aryntra-synapse
git checkout v0.2.0

.\.venv\Scripts\Activate.ps1

uvicorn main:app --reload
```

Ollama must be running locally with `mistral` available:

```powershell
ollama pull mistral
ollama serve
```
